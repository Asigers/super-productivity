# 本地构建与桌面版更新约束

## 1. 适用范围

本文约定：从当前仓库构建 Super Productivity，并更新本机已安装的桌面版。当前操作示例面向 **Windows x64 普通安装版（NSIS）**；微软商店版、便携版、其他系统必须先确认各自的安装与数据目录，不能直接套用。

这是一份更新操作约定，不新增更新器、自动备份服务或 Agent 权限系统，也不替代仓库的 [AGENTS.md](../AGENTS.md)。正式发布另按 [发布手册](release-and-publishing.md) 执行。

**默认流程：检查 → 构建与隔离测试 → 正常退出 → 冷备份与校验 → 原地安装 → 安装校验 → 启动检查 → 汇报。未通过前一阶段，不进入可能覆盖程序或数据的下一阶段。**

## 2. 授权与范围

- “更新本机软件”默认仅授权本地构建、必要检查、备份、安装和启动，不等于授权提交、推送、打标签或远端发布。
- 不擅自拉取远端、切换分支、合并代码、升级依赖、修改版本号或替换锁文件。确需执行时先说明原因并取得确认。
- 必须保留用户已有的已跟踪改动和未跟踪文件。禁止使用整仓恢复、`git reset --hard`、`git clean` 或未经同意的 stash 来“清理环境”。
- 不把更新顺带扩大为功能开发、代码重构、同步设置调整或凭据迁移；不修改 Agent 控制文件。
- 安装涉及新的管理员权限、签名警告、安全软件阻断或可能删除数据时，暂停并让用户决定，不自动代替用户批准。
- 同版本定制构建可以原地覆盖，不为制造“版本变了”的表象执行 `npm version`；该命令可能触发提交、标签和其他生命周期脚本。

## 3. 更新前检查

必须确认并记录下列信息，不能仅按进程名称或默认目录猜测：

| 项目     | 要求                                                                 |
| -------- | -------------------------------------------------------------------- |
| 源码     | 当前仓库、分支、HEAD，以及工作区是否存在已修改或未跟踪文件           |
| 安装形态 | 普通安装版、商店版或便携版；当前版本与 CPU 架构                      |
| 程序位置 | 实际运行的可执行文件路径与安装目录                                   |
| 运行状态 | 属于该安装实例的主进程与子进程；不要误操作其他项目或测试实例         |
| 用户数据 | 根据实际启动参数、配置及运行行为确认目录；优先检查 `--user-data-dir` |
| 环境     | Node/npm、依赖、Electron 运行时、打包工具和可用磁盘空间              |
| 退出方式 | 是否关闭窗口后驻留托盘，是否有同步或退出确认                         |
| 恢复能力 | 可以写入的备份位置，旧程序和数据是否能够完整读取                     |

Windows 的常见数据目录是 `%APPDATA%\superProductivity`，但实际覆盖参数优先；还需排查便携数据目录，不能只备份猜测出的默认路径。

日志和检查输出只记录必要的路径、状态、版本与统计，不输出任务标题、正文、令牌或完整用户数据。

## 4. 构建与安装包验证

### 4.1 使用现有构建链

- 在构建、打包和隔离测试期间，尽量保持用户原程序可用；只在安装前请求退出。
- 使用现有依赖和锁文件。需要安装依赖时遵循仓库流程；不能把 `--ignore-scripts` 后缺失补丁、生成步骤或运行时的状态当作准备完成。
- 确认插件资源、生产前端、Electron 主进程和 preload 都来自本次构建，不能混用旧产物。
- Windows 本机安装优先使用 Windows 原生 Node/npm。经 WSL 调用时明确进入 Windows 命令环境，不混用 Windows/WSL 的运行时和依赖产物。
- 测试、lint 和 E2E 使用 `npm run quiet -- <script> [args]`，完整日志保留在 `.tmp/logs/`。
- 按改动范围运行已有测试与检查。修改 TypeScript/SCSS 时还必须执行仓库规定的 `checkFile`；本地迭代优先使用 `test:affected`，包和 Electron 改动另跑对应测试。

以下命令在**仓库根目录的 Windows CMD** 中执行，适用于已明确选择的本机无签名试用构建：

```bat
npm run quiet -- buildAllElectron:noTests:prod
set "CSC_IDENTITY_AUTO_DISCOVERY=false"
npm run quiet -- dist:win:only nsis --x64 --publish never
```

必须逐条确认成功，不能在生产构建失败后继续打包旧产物。`buildAllElectron:noTests:prod` 包含 lint 和构建，**不运行测试**；`dist:win:only` 仅打包，不代替前置构建。无签名构建不代表官方签名发行版。

若经 WSL 调用，使用 `cmd.exe /c` 包裹单条 Windows 命令。复杂逻辑先写脚本再执行，避免 Bash/CMD/PowerShell 多层转义。Windows PowerShell 5.1 的含中文脚本需使用兼容编码，例如 UTF-8 BOM。

### 4.2 核验实际产物

- 确认生成的是预期平台、架构和安装类型的安装包，记录路径与 SHA-256。
- 检查解包产物中的运行时依赖及本次功能资源；以 [打包配置](../electron-builder.yaml) 和实际归档结构为准，而不是猜测文件名。
- Electron 归档依赖检查使用 [现有检查器](../tools/verify-electron-requires.js)，传入实际 Windows `app.asar`；不能误用指向 Linux 产物的默认脚本路径。
- 需要临时校验包装时放在 `.tmp/`，沿用 quiet 日志方式，不为一次本机更新新增根依赖或永久 npm 脚本。

### 4.3 隔离冒烟测试

使用 [现有桌面冒烟测试](../e2e/electron/packaged-app-smoke.cjs)，遵守 [E2E 指南](../e2e/AGENTS.md)。

- 必须使用独立临时数据目录，不连接真实用户数据，不向真实任务列表写入测试任务。
- 验证打包应用可启动、创建测试任务、重载后恢复任务，以及脚本覆盖的其他桌面行为。
- 当前脚本还断言 URL 中包含 `%23%20packaged%20app`：测试副本应位于名称含 `# packaged app` 的目录。该前置条件变化时以脚本为准，不能删除断言来掩盖夹具使用错误。
- 冒烟脚本中的调试端口、`--no-sandbox` 等参数仅用于隔离测试，不得带入用户日常启动。
- 测试结束只清理本次测试拥有的进程与临时文件，不结束用户实例或其他会话的进程。

**构建成功、测试通过、真实环境联调成功是三件不同的事。** 跳过、未执行和失败都必须如实记录；全量回归未通过时，不能用局部测试或冒烟通过代替。存在未解决失败时，先说明影响和不确定性，取得继续试用的确认；启动、数据或安全相关的阻断不得默认放行。

## 5. 正常退出与冷备份

### 5.1 退出是硬性前置条件

- 安装前通过应用自己的正常退出流程关闭目标实例。
- 关闭主窗口不一定等于退出；需检查托盘和该安装路径的残留进程。
- 若有同步、退出确认或其他交互，暂停并请用户处理；未退出前不得覆盖安装。
- 默认禁止强杀进程、先卸载旧版、删除缓存或清空数据库来“解锁安装”。
- 冷备份开始前和安装器启动前，都要重新确认目标实例没有运行，防止用户在间隙重新打开。

### 5.2 备份内容与位置

备份应位于安装目录和待构建产物目录之外，使用独立时间戳目录；不能放入可能被安装器或构建清理的目标路径。

| 内容         | 约束                                                           |
| ------------ | -------------------------------------------------------------- |
| 旧程序       | 完整程序目录，包括原有 `resources/app.asar`，不能只保存 exe    |
| 用户数据     | 已确认的完整用户数据目录，不只保存应用内导出文件               |
| 本机专属数据 | 确认插件本地凭据、Pi 设置、报告与 Session 等是否包含在备份范围 |
| 安装登记     | 必要的卸载注册信息，用于诊断恢复；不默认导入注册表             |
| 本次安装包   | 可另存并标明“新构建安装包”，不能误称旧版恢复包                 |
| 校验记录     | 版本、路径、文件数量/大小、哈希、时间及检查结果                |

备份可能包含敏感凭据与代码分析内容，只在本地受限目录保存，不上传到远端、不写入仓库、不打印内容。外部 Pi/CWLink 的配置、仓库和凭据不因本次更新被自动搬迁或归档。

### 5.3 校验完成才允许安装

- 检查复制结果；复制工具的退出码按其真实约定解释，例如 Robocopy 的 0–7 不等同于失败。
- 在进程已退出且数据稳定时，对备份中的用户数据逐文件进行 SHA-256 校验，并记录实际数量，不硬编码历史数量。
- 校验旧版关键程序文件与归档，确认备份完整；记录待安装包哈希。
- 备份失败、文件不可读、校验不一致或磁盘不足时立即停止，不以“应该已复制”作为依据继续安装。
- 备份阶段不修改原数据，也不自动删除之前的有效备份。

## 6. 原地安装约束

- 安装前重新确认安装路径、目标实例已退出、备份已验证、安装包哈希未变化。
- 使用本次生成的安装包原地更新，不先卸载；保持已确认的用户数据路径和安装范围。
- 只在安装器确实支持时使用静默参数。NSIS 的目录参数按其约定传入，尤其注意空格及 `/D=` 参数位置。
- 等待安装进程返回并检查退出码。设置合理等待上限，超时先确认是否等待 Windows 交互，不强杀安装器、不并发重复安装。
- 不创建自动启动任务、计划任务或后台更新器，不擅自调整同步、插件权限、模型、凭据或项目设置。
- 安装失败保留日志和备份，说明当前实际状态；不得把“安装器已启动”报告成“更新成功”。

## 7. 安装后验收

### 7.1 启动前

- 确认可执行文件、资源归档存在。
- 对已安装 `app.asar` 计算 SHA-256，与**本次解包构建产物**比较；同时记录与旧版是否不同。
- 确认本次需要的插件资源和主进程模块确实进入安装包。
- 若应用尚未启动，复核原有用户数据文件与冷备份一致，记录结果。
- 若安装器已经自动启动应用，运行期写入可能改变数据或缓存。不得因此自动还原数据，也不能声称完成了冷态一致性复核；需说明验证条件与缺口。

**版本号相同不表示仍是旧代码；版本号变化也不能单独证明装入了正确构建。**

### 7.2 使用原用户数据启动

- 从实际安装目录启动应用，保持原先的数据目录覆盖参数。
- 检查目标进程、主窗口及响应情况，并检查本次启动后的日志，避免把历史错误当成新问题。
- 业务验收应确认数据加载完成、原有任务/项目可见、关键入口可用；只读检查为主，不对真实任务运行写入型测试。
- 窗口响应和业务数据加载完成不是同一结论。若只能验证前者，必须说明后者尚未验证。
- 不为方便验收，在真实数据实例开放调试端口、关闭沙箱或放宽安全策略。
- 涉及 CTeam/Pi 时，安装包包含功能不等于真实联调已通过；没有实际凭据、CWLink 调用和模型运行证据，就明确标注未验证。

## 8. 失败与恢复边界

| 情况                   | 处理                                                       |
| ---------------------- | ---------------------------------------------------------- |
| 构建或隔离测试失败     | 保留原安装，定位失败，不用旧产物冒充新构建                 |
| 应用未完全退出         | 等待用户正常退出，不覆盖安装                               |
| 冷备份失败             | 停止，不进入安装阶段                                       |
| 安装或哈希校验失败     | 保留现场、备份和日志，不重复盲装或自动启动不明产物         |
| 启动失败或原数据不可见 | 先检查启动路径、数据目录、权限及本次日志，不清空数据“重置” |
| 存在未验证项           | 如实标记范围，不能写成全部验收通过                         |

需要恢复时：

1. 先正常退出应用，再另行备份当前程序与当前用户数据。
2. 先评估旧版与当前数据的兼容性；不能假设所有程序回退都无须考虑数据迁移。
3. 若可兼容，优先仅恢复旧程序，不默认回滚用户数据。
4. 确需恢复旧用户数据时，必须提示：会丢失备份之后的新改动，并取得明确确认。数据库文件不能盲目合并。
5. 已启用同步时，还需评估远端和其他设备的状态；本机恢复不代表远端已经撤销。按相应恢复流程处理，不清空远端来掩盖错误。
6. 不自动导入卸载注册表、不自动清理有效备份；提供与本次实际路径一致的恢复说明。

## 9. 完成报告

报告必须区分“准备完成”“已备份”“已安装并校验”“已启动”“业务已验收”，只声明实际达到的阶段。至少包含：

- 安装路径、实际版本及构建来源；同版本定制覆盖需明确说明。
- 安装包/已安装归档的核验结果。
- 备份目录、数据保护校验结果和恢复说明位置。
- 启动结果、业务验收范围和未验证项。
- 测试范围、失败或跳过情况，是否经过真实外部服务/模型联调。
- 当前是否存在需要用户处理的确认或后续配置。
- 是否执行提交、推送或发布；默认应为没有执行。

推荐简报格式：

```text
状态：已安装并完成启动检查；业务数据/真实服务验收状态另列
构建：<版本> / <HEAD> / <是否包含未提交改动>
安装：<路径>；与本次构建归档哈希一致：是/否
数据：<实际用户数据目录>；冷备份及安装后校验结果
备份：<目录>；恢复说明：<文件>
验证：<实际运行的测试及结果>；主窗口/业务加载分别说明
限制：<失败、跳过、未验证和必要的用户操作>
远端操作：未提交、未推送、未发布（按实际情况填写）
```
