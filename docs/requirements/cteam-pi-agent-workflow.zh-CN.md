# CTeam 工单自动分析与 Pi Agent 工作流需求

> 状态：需求草案 / 待技术验证  
> 目标仓库：`Asigers/super-productivity`  
> 目标版本基线：当前 Fork 的 Super Productivity 19.3.1  
> 工作分支：`feature/cteam-pi-work-orchestrator-spec`

## 1. 背景与目标

希望将 Super Productivity 二次开发为个人 AI 工作台：从公司使用的嘉为蓝鲸 DevOps / CTeam 项目管理系统中，定时拉取**分配给当前用户**的工作项，并将其呈现在 Super Productivity 中；对新工单自动派发本地 Pi Agent 做第一轮代码级分析，形成可追溯的分析报告，供用户查看和决策。

核心定位：

- CTeam 是公司工单的唯一事实来源，本项目只读取，不向 CTeam 写回。
- Super Productivity 是个人工作台，负责展示工单、个人处理状态和分析结果。
- Pi Agent 负责理解工单、关联代码仓库并执行只读代码分析。
- 用户自由切换项目和工作线程；后台任务不因切换当前界面而停止。
- 只有遇到需要用户决策、关键资料缺失、严重风险或任务阻塞时才主动通知；普通新工单和普通分析完成不打断用户。

## 2. 目标与非目标

### 2.1 本期目标

1. 定时查询 CTeam 中分配给当前用户的工作项。
2. 支持缺陷、需求、研发任务等常见工作项类型；具体类型以实际 CTeam 部署和 API 返回为准。
3. 新工作项自动进入 Super Productivity，已有工作项按源数据变化更新，避免重复创建。
4. 新工作项自动创建或关联一个 Pi 分析 Session，触发第一轮分析。
5. 支持代码级分析：根据明确配置的 CTeam 项目到本地 Git 仓库映射，阅读代码并给出有证据的分析。
6. 将分析摘要、证据、涉及文件、未知项和建议下一步展示在 Super Productivity 工单详情中。
7. 提供同步日志、分析状态、失败重试、手动立即同步和配置界面。
8. 支持 macOS 和 Windows 桌面版。

### 2.2 本期非目标

- 不向 CTeam 创建、修改、评论、流转或关闭工单。
- 不自动修改代码、提交 Git、推送分支、创建 MR/PR。
- 不自动运行生产操作或未经授权的高风险命令。
- 不拉取分配给其他人的全公司工单。
- 不要求用户使用固定的项目切换顺序或时间表。
- 不把完整 Pi 对话历史复制到 Super Productivity；只展示必要摘要和可追溯链接。

## 3. 用户与工作流

### 3.1 自动拉取

- 默认轮询间隔：15 分钟，可配置。
- 支持启动时同步、手动立即同步。
- 查询范围：仅分配给当前用户的工作项。
- 支持分页、增量查询、限流处理、超时和指数退避重试。
- 如果 CTeam 支持可靠的更新时间过滤或增量游标，优先使用；否则采用分页查询加本地去重。
- 同步失败不能丢失已发现的工单；下次运行应可恢复。

### 3.2 新工单处理

1. Poller 从 CTeam 拉取当前用户的工作项。
2. 通过来源实例标识和工作项 ID 去重。
3. 创建或更新 Super Productivity 中对应任务。
4. 根据工作项类型选择分析模板。
5. 为该工作项创建或恢复专属 Pi Session。
6. 调用本地 Pi Runtime / RPC 派发只读分析任务。
7. 保存分析状态和报告。
8. 普通分析完成不弹出打断式通知；需要决策或发生阻塞时进入 Attention / Needs Me 队列并通知用户。

### 3.3 已有工单变化

- 检测标题、描述、优先级、状态、截止日期、评论或附件等关键内容变化。
- 对影响分析结论的变化，向原 Pi Session 提供增量信息并触发重新分析；不应每次轮询都重新分析。
- 记录每次分析使用的源工单版本或更新时间，避免重复分析相同内容。
- 工单不再分配给当前用户时，默认在本地标记为“已取消分配/不再跟进”或归档，不直接删除用户笔记和分析历史。

## 4. 工作项与任务映射

每个 CTeam 工作项在本地对应一个稳定的 WorkItem 记录，并关联一个 Super Productivity Task 和一个 Pi Session。

建议唯一键：

`source_instance + work_item_type + work_item_id`

字段映射建议：

| CTeam 字段 | Super Productivity / WorkBridge |
|---|---|
| 工作项 ID、类型 | 来源标识、任务元数据 |
| 标题 | 任务标题，保留可检索的工单编号 |
| 项目 | 对应的本地 Project（需配置映射） |
| 描述 | 来源描述或可折叠详情 |
| 优先级 | 来源优先级字段/标签 |
| 状态 | 独立的来源状态，不与个人处理状态混淆 |
| 截止日期 | Due Date（若来源提供） |
| 迭代、版本 | 任务元数据或备注 |
| 原始链接 | 可点击的 CTeam 工单链接 |
| 更新时间 | 源数据版本与增量同步依据 |

### 4.1 字段所有权

必须区分两类状态：

- **源状态（Source State）**：来自 CTeam，例如新建、处理中、已解决、已关闭。
- **个人处理状态（Personal Workflow State）**：来自本地，例如待分析、分析中、待我确认、待补充信息、待验收。

CTeam 同步只能更新源字段，不得覆盖用户自己的备注、思考中断点、个人标签或个人处理状态。

CTeam 工单完成或取消分配时，不应无条件删除本地任务；应保留历史并按配置标记或归档。

## 5. Pi Agent 分析要求

### 5.1 Session 隔离

- 一个 CTeam 工作项对应一个稳定的 Pi Session。
- 同一工作项后续评论、描述或附件变化时，继续使用该 Session，以保留分析连续性。
- 不同工作项之间默认不共享对话上下文。
- WorkBridge 保存 work item 与 Pi Session ID 的映射。
- 使用用户现有的本地 Pi Runtime / RPC 能力，不另造模型运行时。
- 调度器应限制并发数，避免大量新工单同时消耗资源。

### 5.2 分析范围

本期选择：**代码级只读分析**。

Pi Agent 应：

1. 理解工单类型、标题、描述、验收条件、评论和可访问附件。
2. 根据显式配置的 CTeam 项目—Git 仓库映射选择仓库；不得凭项目名称猜测仓库。
3. 读取仓库 README、架构文档、相关模块和代码。
4. 搜索可能相关的接口、类、函数、配置和调用链。
5. 对缺陷单分析复现条件、影响范围、候选根因和验证方法。
6. 对需求单分析业务意图、涉及模块、实现边界和验收标准。
7. 对研发任务分析依赖、工作拆分、风险和实施建议。
8. 输出有证据的报告，并明确区分事实、推测和未知信息。

### 5.3 只读安全边界

- 第一轮分析不修改工作区文件，不创建提交，不推送分支。
- 不访问生产环境，不执行破坏性命令。
- 未配置仓库映射时，只做工单文本分析，并提示缺少仓库关联。
- 任何模型结论都不能伪装成已验证事实。
- 报告中的代码证据应尽可能包含仓库、文件路径、行号或符号名。
- 需要额外日志、权限或复现环境时，标记为“待补充”，不自行绕过权限。

### 5.4 分析报告结构

每份报告至少包含：

1. 工单摘要与类型判断。
2. 问题/需求理解。
3. 相关仓库、模块和代码证据。
4. 初步判断或候选根因（标注置信度）。
5. 影响范围和风险。
6. 尚缺少的信息。
7. 建议的下一步排查或实现方案。
8. 分析时间、源工单版本、Pi Session 引用。

缺陷单、需求单、研发任务可以使用不同分析模板，但应输出统一结构，方便 UI 展示和后续检索。

## 6. 通知策略

遵循低打扰原则：

| 事件 | 默认行为 |
|---|---|
| 发现新工单 | 静默加入列表 |
| Pi 开始分析 | 静默更新状态 |
| 普通分析完成 | 静默保存报告 |
| 需要用户作关键决策 | 通知 |
| 缺少关键资料导致阻塞 | 通知 |
| 发现重大安全/数据风险 | 通知 |
| Pi 异常退出且自动恢复失败 | 通知 |
| 普通轮询失败 | 记录日志，连续失败达到阈值后通知 |

通知应包含工单编号、阻塞原因、需要用户采取的动作和打开详情的入口。

## 7. 建议的产品界面

在保留 Super Productivity 原有任务管理体验的基础上，增加：

- **CTeam Inbox**：我的工单、新工单、源状态、同步时间和筛选。
- **Work Item Detail**：原始描述、评论、附件、源链接。
- **AI Analysis**：分析摘要、代码证据、根因假设、待补充信息。
- **Pi Agent Activity**：对应 Session、分析状态、最近执行记录、失败原因。
- **WorkBridge Settings**：CTeam 地址与认证、轮询间隔、当前用户、项目—仓库映射、Pi RPC 配置、并发数和通知策略。

看板建议提供以下个人处理列：

- 新工单
- AI 分析中
- 待我确认
- 待补充信息
- 已确认 / 待处理
- 待验收

看板列反映个人工作流；CTeam 的源状态应独立展示，不能用本地看板状态代替。

## 8. 技术架构建议

建议在现有 Electron + Angular 架构上扩展，不重写 Super Productivity 的任务模型。

### Renderer / Angular

- CTeam Inbox、工单详情和 AI 分析展示。
- 配置界面、同步状态和 Agent 活动视图。
- 通过受控 IPC 调用主进程能力，不直接持有 CTeam 密钥或任意进程执行权限。

### Electron Main / Work Orchestrator

- CTeam Adapter：认证、查询、分页、字段转换。
- Poll Scheduler：定时轮询、手动同步、重试。
- Work Item Service：去重、变化检测、生命周期管理。
- Pi Adapter：通过本地 Pi RPC 管理 Session、派发分析和读取结果。
- Repository Mapper：显式维护 CTeam 项目到本地仓库路径的映射。
- Analysis Service：选择分析模板、校验报告结构、保存报告。
- Notification Service：仅对决策和阻塞事件通知。
- Persistence：保存映射、同步游标、分析任务和报告元数据。

### 持久化模型建议

至少包含：

- `source_work_item`：来源工单快照和版本。
- `sp_task_mapping`：来源工单与本地任务 ID 的映射。
- `pi_session_mapping`：来源工单与 Pi Session ID 的映射。
- `analysis_run`：分析任务状态、开始/结束时间、源版本。
- `analysis_report`：结构化分析结果。
- `sync_checkpoint`：轮询游标、最近成功时间和错误。
- `repository_mapping`：CTeam 项目与本地 Git 仓库映射。

数据库实现应遵循当前项目的 Electron 持久化和迁移规范；如使用独立 SQLite，必须明确备份、迁移和损坏恢复策略。

### 设计约束

- 优先复用 Super Productivity 已有的 Issue Provider 抽象、任务模型和本地能力。
- 不复制一份独立的任务数据库作为第二套事实来源。
- 不把 CTeam 凭证暴露给 Renderer。
- 本地 Pi RPC 仅监听本机；认证信息安全存储。
- 应用关闭时的后台运行方式需要单独确定：窗口隐藏到托盘继续运行，还是退出即停止；独立系统服务作为后续选项。

## 9. CTeam API 前置验证

当前尚未确认公司实际部署的嘉为蓝鲸 DevOps / CTeam 版本、API 文档和认证方式。实现前必须完成技术 Spike，不得猜测接口地址或字段。

需要确认：

- 产品版本、实际工单模块及工作项类型。
- 查询“分配给当前用户”的 API 和用户身份字段。
- 分页、更新时间过滤或增量查询能力。
- 工作项详情、评论、附件的读取接口。
- 状态、优先级、迭代、截止日期等字段字典。
- SSO、个人 Token 或其他认证方式。
- API 限流、访问审计和公司数据使用要求。

如果没有稳定的增量接口，第一版可以定期分页查询并在本地去重；不要以浏览器抓包得到的临时接口作为长期契约，除非已确认公司允许且接口稳定。

## 10. 隐私、安全与合规

- 只读取当前用户有权访问且分配给当前用户的工单。
- 使用最小权限的只读凭证。
- CTeam Token 存入 macOS Keychain / Windows Credential Manager 或项目认可的安全凭证存储，不以明文写入配置文件和 SQLite。
- 对日志中的工单描述、用户信息、Token 和附件内容脱敏。
- 本地运行 Pi 不代表模型推理一定发生在本地；发送工单或源代码到模型前，必须由用户配置并确认符合公司规定的模型服务。
- 默认不将工单全文、代码或附件上传到未经批准的外部服务。
- 对本地 API、IPC 和 Pi RPC 做访问控制，避免被其他本机进程任意调用。

## 11. 里程碑与验收标准

### M0：技术验证

- 获得并验证 CTeam API 文档和只读认证。
- 能查询当前用户分配的工作项。
- 确认字段映射、分页和更新时间策略。
- 确认 Pi RPC 的创建/恢复 Session 和发送消息方式。
- 确认 Super Productivity 对 Issue Provider 和 Electron Main 扩展的适配点。

### M1：CTeam 自动拉取

验收：

- 默认每 15 分钟轮询，可配置和手动触发。
- 只导入分配给当前用户的工作项。
- 同一来源工单只对应一个本地任务。
- 源字段更新不会覆盖个人备注。
- 取消分配或源工单关闭不会导致本地数据丢失。
- 轮询失败可重试并有日志。

### M2：Pi Agent 自动分析

验收：

- 新工单自动创建或恢复对应 Pi Session。
- 不同工单之间 Session 隔离。
- 同一工单更新可在原 Session 延续分析。
- 支持 Bug、需求和研发任务的不同分析模板。
- 支持并发限制、失败重试和应用重启恢复。
- 分析完成后保存结构化报告。

### M3：代码级分析

验收：

- CTeam 项目必须通过显式映射找到 Git 仓库。
- 能搜索并引用相关代码文件和行号。
- 报告区分事实、推测和未知。
- 第一轮分析不会修改工作区或创建 Git 提交。
- 仓库不存在或无法访问时明确提示，不猜测路径。

### M4：工作台与通知

验收：

- 可以在 Super Productivity 查看工单、分析报告和 Pi Session 状态。
- 新工单和普通分析完成默认静默。
- 关键决策、阻塞和严重风险可以通知用户。
- 用户可以查看失败原因并手动重试。

### M5：授权执行（后续，不属于首期）

- 用户明确批准后，Pi 才能进入代码修改阶段。
- 使用独立 Git Worktree 或隔离工作区。
- 先展示计划和变更范围，再执行。
- 测试、Diff、提交和 MR/PR 各自设置独立授权。
- 不自动向 CTeam 写回。

## 12. 待确认事项

1. 公司 CTeam 的准确产品版本、API 文档和认证方式。
2. CTeam 项目与本地 Git 仓库的映射规则。
3. 应用关闭后是否需要继续后台轮询（托盘常驻或独立服务）。
4. 允许用于工单和代码分析的模型服务及数据边界。
5. 评论和附件是否纳入第一版分析输入。

## 13. 产品原则总结

- 工单自动进入工作台，用户不需要手工导入。
- AI 先分析，代码修改必须经过用户授权。
- 人类自由切换工作线程，后台 Agent 不因界面切换而中断。
- CTeam 负责公司工单事实，Super Productivity 负责个人工作流，Pi 负责分析和执行。
- 只在需要人类判断或任务阻塞时打扰用户。
- 优先复用上游能力，尽量减少对 Super Productivity 核心代码的侵入。
