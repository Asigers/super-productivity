# CTeam 与 Pi Agent 原生集成需求

> 状态：产品需求与技术方案（待 M0 技术验证）  
> 目标仓库：`Asigers/super-productivity`  
> 当前基线：Fork 中的 Super Productivity 19.3.1  
> 核心原则：在保留 Super Productivity 原有任务管理体验的基础上，将 CTeam 工单作为原生 Task 接入，并为 Task 增加 AI 分析与 Pi Agent 能力。

## 1. 产品定位与设计原则

本项目不是在 Super Productivity 旁边再造一套工单系统或项目管理系统，而是增强现有任务，使其能够接收外部工单、自动分析并在用户授权后委托 Agent 执行。

职责边界：

- **CTeam**：公司工单的事实来源。本期只读，不向 CTeam 写入评论、状态、指派或其他变更。
- **Super Productivity**：唯一的个人任务管理入口。继续负责 Task、Project、标签、子任务、计划、看板、时间追踪和完成状态；Project 同时提供 CTeam 项目映射、本机 Pi 启动目录和提示词配置。
- **Pi Agent**：围绕某个 Super Productivity Task 执行代码级分析；后续可在用户明确授权后执行开发工作。
- **集成层**：负责同步、来源映射、Pi 调度和分析数据持久化，不建立平行的任务管理模型。

必须遵守以下产品原则：

1. **原生 Task 是唯一的个人工作对象。** 每张导入的 CTeam 工单创建或更新一条 Super Productivity 原生 Task；列表、详情、Project、Board、Planner 和 Time Tracking 都复用这条 Task。
2. **不增加第二套任务入口。** 不新增 CTeam Inbox、Work Inbox、独立工单列表、独立 Work Item Detail 或另一套看板。
3. **不重做 Super Productivity 的工作流。** 不强制新增固定看板列，不要求用户改变已有任务状态、Project 组织方式或项目切换习惯。
4. **AI 是 Task 的增强能力。** AI 报告和 Pi 执行信息与 Task 关联，但不取代 Task 本身，也不把 Agent 状态混入个人任务状态。
5. **不重复存储任务事实。** 复用现有 Task、Project、Issue Provider、筛选、详情和设置机制；只增加必要的来源映射、分析报告和执行记录。
6. **低打扰。** 新工单导入、Agent 开始分析和普通分析完成默认静默；关键决策、阻塞、严重风险和无法自动恢复的故障默认显示非打断式 Attention，系统通知由用户主动启用。
7. **每个 Project 配置一个 Pi 启动工作目录，不接管代码工作区。** 同 Project 的所有 Task 使用同一配置路径启动，各自保持独立 Pi Session。仓库位置、代码更新和独立 Git worktree 的使用由用户在 `AGENTS.md` 中约定、由 Pi 执行；应用不创建快照、不维护 HEAD/status/Diff 或 worktree 生命周期，也不因启动目录相同而强制 Task 串行。

## 2. 本期目标与非目标

### 2.1 本期目标

1. 定时通过 CTeam 项目内的“经办人”动态搜索字段，查询经办人为当前用户的 Bug、ITR、需求和 Task；不依赖专用“我的工作项”接口。
2. 将 CTeam 工作项通过现有 Issue Provider / 外部任务导入机制创建或更新为原生 Super Productivity Task。
3. 根据明确配置的 CTeam 项目到现有 Super Productivity Project 的映射，将任务放入正确的 Project；每个 Project 配置本机 Pi 工作目录及可编辑的分析提示词。
4. 先提供手动 Pi 分析：应用将工单链接和配置的提示词交给 Pi，Pi 使用本机 CWLink 读取工单，再遵循用户维护的 `AGENTS.md` 分析代码；不为此新建工单内容代理或代码工作区管理层。
5. 在原生 Task Detail 中展示 CTeam 来源信息、AI 分析报告和 Pi 执行摘要。
6. 在现有 Task List / 搜索 / 筛选中支持按来源和 AI 状态过滤，不建立新的任务列表。
7. 在现有 Boards 中继续管理 CTeam Task 和普通 Task；只增加来源及 AI 状态标识，不改变用户已有列和工作流。
8. 在现有 Settings / Project Settings 中配置 CTeam、Pi 工作目录和提示词、Pi Runtime、项目分析授权和通知。
9. 支持同步去重、变化检测、失败重试、手动同步和应用重启恢复。
10. 首期支持 macOS 和 Windows 桌面版。

### 2.2 本期非目标

- 不创建独立 CTeam Inbox / Work Inbox / Work Item 管理页面。
- 不创建独立的 CTeam 任务数据库或第二套个人工作流状态机。
- 不创建独立看板，不强制增加“新工单、AI 分析中、待我确认、待补充信息”等固定列。
- 不向 CTeam 写回任何数据。
- 应用不操作用户代码仓库，不自动 clone/fetch/pull、创建快照、切换分支、创建或清理 worktree，也不建立 Git 状态或 Diff 管理界面。Pi 如何使用仓库由用户的 `AGENTS.md` 和本机 Pi 配置约定。
- 不访问生产环境，不执行未经授权的破坏性操作。
- 不拉取分配给其他人的全公司工单。
- 不把完整 Pi 对话历史复制进 Task Notes。
- 不因启用集成而改变普通 Task 的原有行为。
- 首期不建设独立 Pi 网络服务、独立系统常驻服务或多设备分布式调度系统。

### 2.3 现有方案参考（Prior art）

以下仅用于核对“外部任务如何融入个人工作流”和“Agent 如何关联代码任务”，不据此扩大范围。来源为厂商文档，核对月份为 2026-11，未做产品实机验证。

| 产品与来源                                                                                                        | 个人工作对象与来源关系                                                    | Agent / 代码边界                           | 本方案取舍                                                                |
| ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------- |
| [Sunsama Jira 集成](https://help.sunsama.com/docs/integrations/jira/)                                             | 导入为个人任务，笔记、子任务和时间记录独立于 Jira；允许重复导入同一 Issue | 该集成不提供本方案的代码分析边界           | 借鉴来源与个人安排分离；不借鉴重复导入和完成时写回状态                    |
| [GitHub Copilot](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/kick-off-a-task) | 可从 Issue 或提示发起关联 Session；指派 Issue 会创建 PR                   | 可选择仓库和基准分支，执行结果交给用户审阅 | 借鉴任务关联和显式仓库上下文；首期不采用自动改码、推送或创建 PR           |
| [Cursor Cloud Agents](https://cursor.com/docs/cloud-agent)                                                        | 从现有工作入口发起 Agent，可使用多仓库环境                                | 在独立云端 VM 中运行，可修改分支并交付变更 | 借鉴执行隔离与明确的多仓库范围；不采用默认云端执行或单独 Agent 管理工作台 |

本 Fork 的目标是个人工单处理提效，不是团队协作或通用 Agent 平台。按仓库产品定位，优先保障开发者集成、隐私、离线任务管理和原有操作效率；AI 自动化是否有效，应由真实工单验证，不以新增入口和设置数量衡量。

## 3. 用户工作流

### 3.1 首次同步与 Task 创建

1. 用户在现有 Issue Provider / Integrations 设置中配置 CTeam 连接和只读认证，并确认将工单导入当前 SP 数据集符合公司政策；原生 Task 会随该数据集参与现有同步、导出和备份。
2. 用户在一个已存在的 Super Productivity Project 设置中关联一个或多个 CTeam 项目，并配置本机 Pi 启动工作目录。
3. 用户在工作目录中自行维护 `AGENTS.md`，说明本机 CWLink 的调用方式、仓库位置和分析约定；Project Settings 可编辑发给 Pi 的提示词。启用导入不隐含授权向模型发送资料。
4. 在指定执行设备上，复用现有轮询机制，按当前 CTeam 用户 ID 搜索各已映射项目/工作项类型的“经办人”字段，并只处理授权同步范围内的结果；不得退化成全项目或全公司查询后仅在本地筛选。
5. CTeam Provider 根据映射找到目标 Super Productivity Project，复用原有任务创建/更新路径，创建原生 Task。
6. 通过第 4.1 节定义的稳定来源标识去重；重复轮询、重启和不同视图均引用同一个 Task ID。
7. 新工单进入原有 Project 列表；自动导入不擅自加入 Today 或安排截止日期，继续沿用既有 backlog / 计划语义。

未映射项目不自动创建 Project 或独立 Inbox。只保存恢复导入所需的最小待处理标识和诊断信息；映射完成后重新执行经办人候选分页，并按稳定来源键幂等导入，不得遗漏映射完成前已可见的候选。

映射规则：一个 CTeam 项目在同一来源实例内只映射到一个 Super Productivity Project；一个 Super Productivity Project 可以汇集多个 CTeam 项目。首期不支持按工单类型或字段拆分同一个来源项目。

CTeam 状态排除是用户可编辑的配置，不是硬编码名单。按 CTeam 项目和工作项类型（以实时 `modelTypeId` 区分）分别选择需要排除的状态；设置界面从 CTeam 当前可用状态中选择并保存稳定状态标识，显示名称只作说明。“已完成”“已关闭”“测试完成”仅作为可选的建议预设，用户可增删。状态定义无法解析或发生变化时，暂停该项目/类型的新增导入并提示重新确认，不得静默丢掉排除规则。状态排除必须在创建 Task 和触发 AI 之前生效。

首次连接、补齐映射或扩大同步范围产生的历史批量导入，默认不触发批量 AI 分析。用户先确认分析范围；自动分析只对启用后新发现且符合条件的工单生效。

### 3.2 新工单与 Pi 分析

1. Task 导入后，未启用或未授权 Pi 时只管理原生 Task，不自动调用模型。
2. 用户从 Task Detail 启动分析，应用以当前 Project 配置的本机工作目录作为 Pi 的启动 `cwd`，为该 Task 使用独立 Session。
3. 应用发送工单原始链接、配置的分析提示词及本次用户指示，不先替 Pi 获取、拼装完整工单内容。
4. Pi 遵循用户维护的 `AGENTS.md`，调用本机 CWLink 读取链接对应的工单，再定位并分析相关代码。仓库更新、独立 worktree 的创建/复用/清理由 Pi 按用户约定处理。
5. 同 Project 的不同 Task 可以并行；应用不设置 Project 级串行锁，不假定启动目录就是所有 Task 共用的代码检出目录，也不采集 Git 状态。
6. Pi 返回分析报告，应用将其关联到当前 Task 并在现有详情面板中展示。Agent 不改变个人完成状态、计划或看板列；普通分析完成不触发打断式通知。

CWLink 不可用、认证失败或代码无法访问时，Pi 应说明缺少的信息，不能假装已取得工单或完成代码级分析。首期不另造工单读取 fallback 服务。

### 3.3 已有工单更新

- 定期刷新 Provider 已知的来源版本；首期以来源版本变化提示报告可能过期，不承诺追踪 Pi 经 CWLink 读取的全部资料。
- 更新必要来源信息，不覆盖用户的 Notes、子任务、时间记录、计划、标签和完成状态。
- Task 标题采用三方比较：当前本地值、上次实际写入 Task 的来源标题基线、新来源值。本地仍等于基线时才更新；本地已改名则保留本地值，仅更新来源显示。基线必须考虑导入时的前缀和格式转换，不可直接用未经转换的源标题比较。
- Provider 已知的来源内容变化或用户修改分析提示词时，旧报告可标记为可能过期；已授权自动分析时合并变化后再排队。单纯状态、优先级变化不触发无意义的模型调用。代码和 `AGENTS.md` 变化不由应用检测，用户按需重新分析。
- CTeam 排除状态控制候选 Task 的首次导入和自动分析资格，不将已导入的原生 Task 自动完成、归档或删除。已关联 Task 继续按已知来源 ID 尝试只读刷新状态；若状态进入排除集合，更新来源显示并停止新的自动分析，保留用户的 Task 和报告。
- 来源项目或映射改变不强制移动既有 Task；用户手动移动 Project 后保留个人选择，后续分析使用当前所属 Project 的授权和上下文。
- 取消分配、关闭、删除和权限丢失必须通过已验证的单据事实区分；候选搜索中不再出现某 Task 本身不足以证明任何一种状态。

### 3.4 用户处理

用户始终通过 Super Productivity 原有入口工作：

- 从原有 Task List 打开任务。
- 从现有 Project 查看该项目下的 CTeam Task。
- 从现有 Board 管理任务状态。
- 从 Planner 安排工作。
- 使用原有 Time Tracking 记录投入。
- 在 Task Detail 中查看 CTeam 信息和 AI 分析。
- 根据分析结果自行决定下一步，或明确授权 Pi 继续执行。

### 3.5 来源缺席与本地生命周期

- 经办人搜索中未出现某个工单，只能表示本次候选查询没有返回它；不能据此判定关闭、删除、取消分配或失去权限。分页失败、403、404、字段配置失效或权限变化应标记为未知/不可访问，保留本地任务。
- 仅当公司允许的详情接口或变更事件能确认原因时，才更新具体来源状态；不得为识别取消分配而扩大为全公司工单查询。
- 本地归档不解除来源关联，轮询应同时检查活动任务和归档记录，不重复创建或自动恢复已归档 Task。
- 用户删除或明确忽略自动导入的 Task 后，保存最小来源抑制记录，避免下一轮立即重建；撤销删除或用户显式重新导入时解除相应抑制。
- Task 删除时停止相关排队/运行任务，结果不得重新创建 Task。Project、Provider 或授权删除/撤销后，同样取消受影响的运行并禁止新的资料发送。

## 4. CTeam 与原生 Task 的映射

### 4.1 一对一映射

一个来源工作项只对应一个原生 Task。概念唯一键为：

`sourceInstanceId + cteamProjectKey + issueId`

- 来源实例使用稳定逻辑 ID，不使用可编辑显示名称、本地路径或临时凭证。
- 本机 CWLink 参考实现通过 CTeam 项目键和内部工作项 `id` 读取详情；API 路径始终同时需要二者。首期按项目作用域组成来源键，不假定内部 `issueId` 全局唯一；CTeam 编号（如 `p17_32312`）用于显示/查找，不代替内部 ID。
- 工作项类型依据详情中的 `modelTypeId` 判断，不能把类型或可能变化的分类放进唯一键。M0 仍需用当前部署数据验证 ID 在项目内的稳定性和类型变更行为。
- Provider 配置被复制、Project 映射改变或认证更新，不能使同一来源工作项获得新身份。
- 优先复用现有 `issueProviderId`、`issueId`、`issueType` 关联，验证其与稳定来源键的关系；不能假定 Provider 配置 ID 就等于来源实例 ID。
- 自动导入应采用稳定 Task ID 或等价的幂等路径；并发、重启及恢复场景不能只靠“先查询、后随机建 Task”去重。
- 同一工单在 Task List、Board、Planner 和 AI 区域始终引用同一个 Task ID。首期只有一台指定执行设备自动轮询和调度，详见第 8.5 节。

### 4.2 来源元数据

优先复用现有 Task 的 `issueId`、`issueProviderId`、`issueType`、`issueLastUpdated` 和 `issueLastSyncedValues`。CTeam 特有的来源项目键、原始标题、状态、优先级、URL 和版本信息由 Provider 返回，按需加载或有限缓存，不优先给核心 Task 增加 `provider: 'cteam'` 专用结构。

只有现有关联不足以表达稳定身份、标题基线或删除抑制时，才增加最小扩展或 sidecar；M0 须列明事实来源、写入者、同步和清理规则。不能同时把相同来源关联维护在 Task 字段、插件数据和新映射表中，形成多个事实来源。

涉及现有持久模型的新字段必须可选并有运行时默认；旧客户端和未安装插件的客户端应能继续管理 Task。不得仅为新增元数据提高同步 schema 版本，或建立完整的本地 WorkItem / Task 模型。

### 4.3 字段所有权

| 数据                                | 所有者                           | 同步规则                                                                                |
| ----------------------------------- | -------------------------------- | --------------------------------------------------------------------------------------- |
| 来源身份、类型、原始链接            | CTeam                            | 用于稳定关联和类型判断，类型变化不产生新任务；首版来源界面仅展示第 5.5 节约定的基本信息 |
| 来源状态、来源优先级                | CTeam                            | 更新来源信息，不映射个人完成状态                                                        |
| 来源版本、本次请求记录              | CTeam / 集成层                   | 用于已知来源变化和运行关联；不代表完整代码或 CWLink 读取内容的指纹                      |
| Task 标题                           | 初始来自 CTeam，之后允许本地调整 | 按标题基线保护本地修改，不静默覆盖                                                      |
| Task 所属 Project                   | 用户                             | 首次导入按映射放置；后续不覆盖用户移动                                                  |
| Task Notes / 个人备注               | 用户                             | CTeam 同步不得覆盖                                                                      |
| 子任务、标签、计划、时间记录        | 用户 / Super Productivity        | 完全沿用原有行为                                                                        |
| Task 完成状态及 Board 列            | 用户 / Super Productivity        | 不由 CTeam 或 AI 自动覆盖                                                               |
| AI 报告、运行记录和 Pi Session 关联 | 本机集成层                       | 独立保存，通过 Task ID 关联，不默认跨设备同步                                           |

来源状态、个人任务状态、分析运行状态、报告有效性和 Attention 分开表达；不能合并成一套任务状态机，也不必把 Pi 的每个内部事件转成新的用户状态。

## 5. 与 Super Productivity 原有功能的融合要求

### 5.1 Task List、搜索与筛选

不新增 CTeam Inbox 或第二套工单列表。在现有能力允许的范围内支持：

- 来源：全部 / CTeam / 普通任务。
- 分析运行：未分析 / 排队中 / 分析中 / 已完成 / 已阻塞 / 失败 / 已取消 / 已中断。
- 报告：无报告 / 有效 / 已过期；允许“分析中且上一份报告过期”同时成立。
- 需要我处理：存在未确认的关键决策、资料阻塞、严重风险或 Agent 故障。

筛选结果仍为原生 Task，沿用原有排序、分组、批量操作和详情。先复用已有来源标识和详情入口，筛选器扩展放在 M4；不为筛选动态写入用户标签或同步高频 Agent 状态。

未配置 Pi、未获本机授权或不支持桌面执行时，显示相应能力/准入提示。其他设备只有同步来的 Task 而没有本机运行记录时，显示“本机无分析记录”，不推断所有设备均未分析；具备能力且尚未运行的 Task 可显示未分析，但读取或筛选 Task 不会自行派发分析。

### 5.2 Project：任务组织、外部映射与 Pi 配置

本集成复用 Super Productivity 原生 Project 组织任务、关联 CTeam 项目并配置 Pi 的启动目录和提示词，不另建项目模型，也不在应用中管理代码仓库上下文。

#### 5.2.1 CTeam 项目映射

- 在现有 Project Settings 中配置 CTeam 实例和一个或多个 CTeam 项目键（CTeam URL 的 `/vteam/<projectKey>/`；CWLink API 路径参数虽命名为 `projectId`，使用的是该项目键），不另建配置入口。不得把数字 DevOps Project ID 当作项目键。
- 该来源项目的“经办人”搜索字段和排除状态集合按 `projectKey + modelTypeId` 管理；一个 Project 汇入多个来源项目时，各自保留独立规则。
- 映射优先以现有 Issue Provider 配置为唯一事实来源，复用 `defaultProjectId`；Project Settings 只是同一配置的项目视图，不再向 Project 写入重复的来源项目清单。
- 一个 CTeam 项目在同一来源实例内只能映射到一个 Super Productivity Project。保存时校验冲突，不由轮询时的先后顺序决定归属。
- 一个 Super Productivity Project 可以汇集多个 CTeam 项目，并同时包含普通 Task；优先用 Provider 配置的项目过滤覆盖这一场景，不建设新的规则路由引擎。
- 首期不支持按工单类型、标签或其他规则拆分同一来源项目，也不自动创建 SP Project。
- 映射修改只影响后续导入；迁移既有 Task 由用户显式执行普通 Project 移动操作。

#### 5.2.2 Project 的 Pi 工作目录

每个 Super Productivity Project 配置一个持久的本机 Pi 启动工作目录，同 Project 的所有 Task 均使用该配置。路径按设备本地保存，不同步绝对路径。

工作目录由用户准备和维护；它可以容纳指引、脚本或仓库引用，不要求它本身就是某个 Git worktree。一个或多个代码仓库的位置、使用哪个分支、是否更新代码、如何创建独立 worktree，都写在用户维护的 `AGENTS.md` 中，交由 Pi 执行。

应用仅验证配置的目录可访问并据此启动 Pi，不管理源 clone、remote、分支、HEAD、未提交改动、快照或 worktree。启动目录相同不意味着不同 Task 必须在同一代码检出目录操作，也不构成 Project 串行运行的理由。

使用本地代码不要求在 Super Productivity 中配置 GitLab Token；Pi 如需访问远程仓库，沿用用户已有的本机 Git/Pi 配置，应用不代管 Git 凭证或注入提示词。

#### 5.2.3 用户维护的 Agent 指引与可配置提示词

- 用户直接在 Project 工作目录中维护 `AGENTS.md` 及其引用文件，说明业务背景、仓库位置、本机 CWLink 用法、代码更新和 worktree 约定等。
- 应用不生成 `SP_AGENT_INSTRUCTIONS.md`，不覆盖、同步或版本化管理这些文件，也不扫描文件变化来触发分析。
- Project Settings 提供可编辑的分析提示词，启动时将工单链接等 Task 参数代入后发送给 Pi；用户可追加本次运行的指示。第一版默认提示词见第 6.2 节。
- 应用维护的是“发给 Pi 什么请求”，不是“Pi 按哪些步骤管理代码”；是否需要独立 worktree、如何使用本地工具，由 Pi 遵循用户指引处理。

#### 5.2.4 Task 分析时的上下文组合

应用提供：

1. 当前 Task ID 和 CTeam 工单原始链接。
2. 当前 Project 配置的分析提示词。
3. 用户对本次分析的额外指示。

Pi 从启动目录读取用户维护的 `AGENTS.md`，使用本机 CWLink 获取工单信息，并按指引访问代码。应用不注入仓库状态，不重复组装评论、附件或代码上下文。

不同 Task 使用独立 Pi Session，不混用对话历史；同 Project 的 Task 可以并行。需要独立代码环境时，用户可在 `AGENTS.md` 中约束 Pi 使用独立 worktree，应用不分配或跟踪它们。

#### 5.2.5 Project 配置与跨设备边界

在现有 Project Settings 中保留必要配置，不新增独立项目管理页面：

- **CTeam Projects**：关联的 CTeam 实例和项目键，复用 Provider 配置。
- **Pi Working Directory**：该 Project 下所有 Task 启动 Pi 时使用的本机目录。
- **Pi Prompt**：可编辑的分析提示词。

目录路径、执行设备开关和本机分析授权不参与 SP 同步。CTeam 项目映射及提示词如沿用现有同步机制，新增持久字段须可选并提供默认；同步收到配置不等于授权在本机执行。

`AGENTS.md`、代码仓库、worktree 和本机 CWLink 配置由用户维护，应用不负责同步、备份或清理。凭证不写入可同步的 Project 数据，详见第 5.7.1 节。

### 5.3 Boards

- 直接使用 Super Productivity 原有 Boards。
- CTeam Task 与普通 Task 混合显示。
- 不新增专用 CTeam Board，不强制固定看板列。
- 用户现有列、列顺序、状态和拖拽行为保持不变。
- Task 卡片可显示轻量来源标识（例如 CTeam）和 AI 状态徽标。
- AI 分析中、已完成、阻塞等状态不得自动映射成 Board 列，也不得擅自改变 Task 的完成状态。

### 5.4 Planner 与 Time Tracking

- CTeam Task 可以像普通 Task 一样加入 Planner / Schedule。
- 原有预计耗时、实际耗时、计时器、日历和统计功能保持不变。
- 同步 CTeam 数据不得重置任务计划或时间记录。

### 5.5 Task Detail

不新增独立 Work Item Detail 页面。在保留原有子任务、标签、备注、预计耗时和时间追踪的基础上，复用 Task Detail 已有的 Issue 来源区域，再增加必要的可折叠 AI 区域；不重复显示两套来源详情。

**A. CTeam Source**

首版仅展示：

- 工单编号。
- 工单标题；来源标题与用户本地修改的 Task 标题保持区分。
- CTeam 来源状态，不映射个人完成状态。
- 原始链接，点击后跳转 CTeam。

不在首版来源区域展示完整描述、评论、附件列表或新增下载入口，也不为这些内容建设工单阅读器。Pi 需要的详情由它通过本机 CWLink 读取；来源内容不复制到 Task Notes。本期 CTeam 保持只读。

**B. AI Analysis & Pi Agent**

- 展示模型最终输出的 Markdown 正文，内容和组织方式由模型结合用户提示词自行决定。
- 不将报告拆成固定的“摘要、根因、置信度、代码证据”等字段，不要求固定 JSON、必填章节或报告 schema，也不以缺少这些字段为由拒绝结果。
- 复用现有 Markdown 展示能力，保留模型生成的标题、列表、表格和代码块等表达；按现有安全规则渲染，不执行输出中的脚本或命令。
- 正文之外单独展示必要的运行状态、时间、历史入口、Pi Session 关联和最近执行事件摘要；这些是应用的运行信息，不约束报告内容。
- 操作：继续分析、重新分析、停止运行；查看 Pi Session 以选定版本实际能力为准。打开交互终端前必须完成 Session 写入权交接，不允许终端和后台同时写同一个会话文件。

Markdown 结果独立、按运行保存，不追加到 Task Notes，也不为了适配界面将模型正文转换成固定模板。新建 Pi 对话遵循 Pi 自身的 Session 存储规则；旧版对话保留在原集成目录并继续在那里恢复。SP 仅保存报告和必要的运行关联，并遵循第 8.4 节的保留边界。

### 5.6 全局 Agent 状态入口

不建设独立 Agent Activity 页面或 Agent 管理工作台。

可以在现有工具栏/状态区域增加轻量状态指示器，显示：

- 正在运行的 Agent 数量。
- 是否存在需要人工介入的阻塞或故障。
- 点击后定位到相关原生 Task。

详细执行记录放在对应 Task Detail 的 AI Analysis & Pi Agent 区域。不得要求用户通过监控大屏管理 Agent。

### 5.7 Settings

不新增独立 WorkBridge Settings 一级页面。配置融合到现有设置体系：

| 现有设置位置                   | 增加配置                                                                                                         |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| Issue Providers / Integrations | CTeam 服务入口校验、只读认证与本机凭证设置、当前用户 ID、连接测试、同步范围和手动同步                            |
| Project Settings               | CTeam 项目映射、按工作项类型配置的经办人搜索字段与排除状态、本机 Pi 启动工作目录、可编辑分析提示词和项目分析授权 |
| AI / Agent 或现有集成设置      | Pi 可执行入口与兼容版本检测、允许的模型、全局最大并发和运行总时限                                                |
| Notifications                  | 用户主动启用的关键决策、阻塞、严重风险和无法恢复的故障通知                                                       |
| 现有诊断/日志区域              | 最近成功时间、同步/Agent 失败原因、队列恢复和显式重试                                                            |

Pi 首期通过本机子进程 RPC 接入，不配置假定存在的 HTTP 服务地址或 RPC Token，也不预设原生 RPC 有通用的“Agent 列表”能力。

#### 5.7.1 本机凭证管理

- 允许本项目自行管理凭证，优先复用现有 `PluginAPI.setSecret/getSecret/deleteSecret` 等本机秘密存储；不强制 macOS Keychain 或 Windows Credential Manager。
- 现有插件秘密存储不参与 SP 同步、导出和备份，但静态内容目前未加密。首期允许沿用这一边界，必须如实说明它不能抵御同账户文件读取、恶意插件或本机入侵；不能宣称为系统钥匙串或强隔离。
- 凭证按插件、来源实例和账号区分；普通 Provider / Project 配置只保存非秘密连接参数或凭证引用，不能因表单使用 password 类型就把 Token 写入可同步配置。
- 受信任的 CTeam Provider 沿用现有秘密 API 管理其请求认证；应用不将 Provider Token 拼入 Pi 提示词、工单文本、报告或日志。Pi 分析时的 CTeam 访问由本机 CWLink 使用其已有认证配置完成，不另造凭证转交层。
- Pi 的模型认证和本机工具使用沿用用户已有的 Pi 配置；CWLink 认证由 CWLink 自身管理。应用不复制认证秘密到提示词，也不要求用户在 SP 中重复配置 CWLink 凭证。
- 提供本机更新、删除凭证和断开连接能力。断开当前实例时停止请求并清理其凭证，不影响其他实例；换设备需重新认证。
- 后续可在相同接口后升级存储保护，但不为首期自造加密算法，也不把与密文同处保存的固定密钥当作有效安全保证。

## 6. AI 代码级分析

### 6.1 Session 隔离与生命周期

- 每个 Task 在当前设备维护独立 Pi Session；启动 `cwd` 使用所属 Project 配置的工作目录。共享启动目录不等于共享对话或强制共享代码工作状态。
- 不设置 Project 级串行锁；同 Project 的不同 Task 可以并行，仅受全局可配置并发上限约束。Pi 可按用户的 `AGENTS.md` 使用独立 worktree，应用不参与分配。
- 同一 Task Session 不同时接受两次活动运行，避免并发写入同一会话文件；这一限制不扩展为整个 Project 的锁。
- 延续 Session 时提供本次工单链接和用户指示，旧报告只作历史线索；本次应读取哪些工单与代码信息由 Pi 按指引判断。
- Task 移动 Project 时，后续分析使用目标 Project 的启动目录和提示词，并新建 Session；应用不搬移任何代码或 worktree。
- 保存 Session ID 和持久会话关联，不把示例中的 `--no-session` 当作可恢复配置。
- 用户停止运行时，先清除相关待执行消息，再中止活动分析并等待结束；不能仅终止当前回合却继续执行排队内容。
- 重启后核对队列与会话关联；未确认结束的运行先标记为中断，规则见第 6.8 节。托盘常驻与真正退出遵循第 8.5 节。

### 6.2 第一版：工单链接 → 本机 CWLink → 代码分析

应用只发送工单链接、可配置提示词和本次用户指示，不负责为 Pi 抓取完整工单、筛选评论附件或准备代码快照。

Pi 使用用户本机已有的 CWLink，读取链接对应的 CTeam 工单；具体调用方式、认证和可用信息以本机 CWLink 为准，在 M0 用真实链接验证。不为分析路径新增 CTeam HTTP 代理、MCP 服务或自定义读取工具。Provider 仍负责原生 Task 的发现、导入和来源刷新，两条路径职责不同。

默认提示词示例（用户可在 Project Settings 编辑）：

```text
请分析当前 CTeam 工单：{{issueUrl}}
当前 Super Productivity Task ID：{{taskId}}

请遵循工作目录中的 AGENTS.md：
1. 使用本机 CWLink 读取该链接对应的工单信息。
2. 按项目约定定位并分析相关代码。
3. 返回工单理解、代码证据、可能的原因或实现思路、风险和下一步建议。
若工单或代码无法读取，请明确说明，不要假装已完成分析。
```

`{{issueUrl}}` 和 `{{taskId}}` 来自当前 Task 的稳定关联；替换后通过 Pi RPC 消息发送，不将链接拼入应用执行的 Shell 命令。

工作目录中的 `AGENTS.md` 由用户自行维护，可规定使用独立 worktree、是否更新代码和如何验证。应用不读取或维护 HEAD、Git status、Diff、worktree 清单或本地代码版本，也不因这些信息变化触发重分析。

### 6.3 分析任务类型

Bug、需求和研发任务可以在用户配置的提示词或 `AGENTS.md` 中约定不同分析侧重点；第一版不必为此建立独立模板路由或固定执行步骤。

### 6.4 Pi 本机配置与职责边界

- Pi 沿用用户已有的本机工具、指引和扩展配置；第一版不另建按 Task 分配文件写入、Shell、网络、Git 和测试能力的权限系统，也不重写一套受限工具。
- 用户通过 `AGENTS.md` 约定仓库操作和独立 worktree 使用，Pi 自行判断是否更新代码、如何分析及验证；应用不代替 Pi 决定这些步骤。
- `cwd`、`AGENTS.md` 和 Git worktree 不是安全沙箱。首期以用户信任的本机 Pi/CWLink 环境为前提，不宣称提供操作系统级隔离。
- CTeam 读取仅使用 CWLink 的只读能力；不得因工单文本中的指令执行评论、流转或其他写回操作。凭证不放入提示词、报告或日志。
- 发送工单和代码前确认允许的模型服务及数据用途。报告区分事实、代码证据、假设和未知，明确哪些验证实际执行、哪些只是建议。

### 6.5 分析状态与人工介入

状态按三个独立维度表达：

| 维度       | 概念值                                                                                           | 含义                                                                    |
| ---------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| 运行       | `NOT_STARTED`、`QUEUED`、`RUNNING`、`COMPLETED`、`BLOCKED`、`FAILED`、`CANCELLED`、`INTERRUPTED` | 尚未分析、排队、执行、完成、资料阻塞、失败、用户取消、进程/应用意外中断 |
| 报告有效性 | `NONE`、`CURRENT`、`STALE`                                                                       | 没有报告、匹配当前输入、输入变化后已过期                                |
| Attention  | 无，或附原因的待确认标记                                                                         | 关键决策、阻塞、严重风险或需处理的故障                                  |

`STALE` 不是运行状态。例如可同时显示“新分析运行中”和“上一份报告过期”；新分析失败也不删除上一份可查看的报告。

缺少本机配置或授权是能力/准入提示，不伪装成运行失败；`COMPLETED` 以运行正常结束且收到非空最终文本为准，不把 RPC 接受请求、单次中间回合结束或模型自述成功当作完成。应用不校验报告 JSON、固定字段或 Markdown 章节结构。

Attention 不改变 Task / Board 状态，需支持确认和按原因、版本去重。

### 6.6 分析触发规则

自动分析默认关闭，由用户在确认模型服务和资料范围后，通过 Project 的本机 Pi 开关主动启用；手动分析同样须获准发送数据。用户在 2026-11-04 明确要求新导入 CTeam Task 自动分析，不再逐条手动点击。当前触发范围是本机真正新建 Task 的导入事件，包括手动和后台导入；不是观察 Task 列表或同步状态来补跑。

| 事件                                             | 默认行为                                                                                                                       |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| 首次连接、补齐映射或扩大范围后的历史导入         | Pi 关闭时只导入 Task；Pi 已开启时，本机每个新建 Task 都首次分析，批量导入可能并发消耗模型额度。历史补导入不应分析时须先关闭 Pi |
| 启用自动分析后新导入的工单                       | 自动启动首次分析，不要求逐条点击；同 Project 不同 Task 可并行                                                                  |
| 应用启动、同步收到任务、恢复备份、已有 Task 刷新 | 不触发首次分析；切换开关不自动回填先前导入的 Task                                                                              |
| Provider 已知来源内容变化                        | 提示旧报告可能过期；已授权自动分析时合并变化后排队，Pi 自行通过 CWLink 读取最新信息                                            |
| 优先级或非排除来源状态变化                       | 更新来源信息，不因此调用模型                                                                                                   |
| 状态进入该来源项目/类型的排除集合                | 不导入尚未关联的 Task；已关联 Task 保留并更新来源显示，停止后续自动分析，不改变个人完成状态                                    |
| 可靠确认关闭或取消分配                           | 停止后续自动分析，保留个人 Task 和已有报告                                                                                     |
| 模型服务或资料授权改变                           | 暂停受影响的自动分析，待用户重新确认                                                                                           |
| Project 提示词或启动目录配置变化                 | 后续分析使用新配置，旧报告可提示配置已变，不自动全项目重跑                                                                     |
| 代码、worktree 或 `AGENTS.md` 文件变化           | 应用不检测、不维护状态；由用户按需重新分析                                                                                     |
| 用户手动重新分析                                 | 新建运行和报告版本；即使请求相同也允许显式重试                                                                                 |
| 同一 Task 连续变化                               | 同时只保留一个最新待处理请求，旧结果不得覆盖新请求结果；不锁住同 Project 的其他 Task                                           |

第一版不承诺自动判断报告是否仍匹配全部本地代码或 CWLink 读取内容；“有效/过期”仅基于应用已知的来源和请求变化。

### 6.7 模型自由输出的 Markdown 结果

最终形态是模型自行组织的 Markdown，而不是固定 JSON 或由应用拼装的报告模板。模型可根据工单特点、用户提示词和 `AGENTS.md` 自由选择内容与表达方式；应用不规定必填字段、固定标题、章节顺序或结构化报告 schema。

提示词可以说明希望关注问题理解、代码证据、风险或下一步，但这些是用户可编辑的分析指引，不是结果接收和展示的格式门槛。应用直接保存并展示最终 Markdown 正文，不要求模型额外输出结构化摘要，也不为界面字段反向限制模型发挥。

应用在正文之外保存 Task/Project ID、工单链接、运行 ID、时间、当次发送的提示词、模型和 Pi Session 引用，用于关联与历史查看；这些元数据不需要模型在正文中按固定格式返回。

以运行结束状态和是否收到非空最终文本判断是否取得结果，不以 Markdown 是否符合模板判断成功。运行失败、中断或输出截断时保留已收到的文本并标明运行状态，不因缺少固定章节而重试或自动修复报告。正文中的链接和代码按不可信内容安全渲染，不执行命令。

### 6.8 调度、幂等与重启恢复

以下为首期预算初值，M0 需用代表性工单验证；调整应记录依据并保持有限，不另建配置工作台。

- 全局最大并发可配置，不另设 Project 串行锁；同 Project 的不同 Task 可以并行。单次运行总时限初定为 10 分钟，Pi 瞬时模型错误最多自动重试 2 次并计入总时限，协调器不叠加整轮重试；M0 验证所选版本能落实这些预算。
- 每次运行分配独立 `runId`，发送前持久化请求和队列记录；去重依据为 Task ID、来源关联及已知版本、Project 启动目录配置、本次实际发送的提示词和模型。不包含 HEAD、工作区状态或 `AGENTS.md` 内容指纹。
- 相同输入的自动请求合并；用户手动重新分析可以产生新运行。同一 Task 同时只有一个活动运行和一个最新待处理目标，不能无限堆积更新。
- 在发送 prompt 前订阅事件，按请求 ID 关联响应；接受请求不等于结束，`agent_end` 之后可能继续重试，须结合最终消息、`agent_settled` 和运行结束状态确认最终文本，不解析报告 JSON 或校验固定内容结构。
- 重启后先核对运行记录、Pi 会话条目和已有报告。RPC 请求 ID 不是服务端幂等键；不能因没收到响应就假定 Pi 没执行并重发。
- 无法确认旧运行结果时标记 `INTERRUPTED`，保留可核对信息，由用户显式重试；不承诺跨崩溃“恰好执行一次”。
- 报告按 `runId` 幂等落库。结果返回时重新检查 Task 是否存在、Project/授权和输入是否仍匹配；旧版本只能作为过期历史保存，不能成为当前报告或触发新的通知。
- Task 移动、权限撤销、停止和真正退出时取消相关待处理消息与进程；无效授权下不继续发送资料。事件流持续读取但合并更新，避免积压 stdout 或将每个 token 持久化。

## 7. 通知与 Attention

复用现有通知能力。Attention 默认在任务详情/状态标识中非打断式显示；系统通知必须由用户主动启用，不因启用 CTeam 或 AI 集成而自动开启。

| 事件                                  | 默认行为                                                                                                                                             |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 新工单导入                            | 按用户 2026-11-04 的要求提供独立本机通知开关，默认关闭；开启后按 Project 合并同批导入，只显示数量，点击定位原生 Task，系统通知不可用时显示应用内提示 |
| 分析开始、普通分析完成                | 静默更新 Task / 分析区域，不扩展为持续通知                                                                                                           |
| 关键决策、资料阻塞、重大安全/数据风险 | 设置带原因的 Attention；已启用通知时提醒                                                                                                             |
| Pi 异常且有限恢复失败                 | 设置故障 Attention，提供显式重试                                                                                                                     |
| 普通轮询失败                          | 记录不含用户内容的诊断；连续失败达到阈值后设置故障 Attention                                                                                         |

按 Task、原因和输入版本去重，用户确认后不因下一次轮询重复提醒；新原因或新版本可重新置位。原始 Pi 通知不能绕过 SP 的通知策略。点击提醒直接打开原生 Task，不建设第二套 Attention 列表或监控工作台。

## 8. 技术架构建议

以下描述职责边界，不要求每个名称都新建一个 Service、数据库表或后台进程。优先沿用当前架构和数据流，不重写任务管理层。

### 8.1 CTeam Issue Provider

- 按[新增集成指南](../add-new-integration.md)实现 Issue Provider 插件，优先放在现有插件包体系中；不默认向核心 Provider union、默认配置和 Angular 服务增加 CTeam 分支。
- 复用搜索、按 ID 查询、自动导入、批量刷新和现有来源详情；优先使用现有 `getNewIssuesForBacklog`、`getById/getByIds` 和 `defaultProjectId` 能力。
- CTeam 候选发现按项目和 `modelTypeId` 动态字段过滤“经办人 = 当前用户”；配置需取自实时搜索字段元数据，不硬编码 `经办人` 的字段 ID 或筛选值格式。不能确认精准身份匹配时停止该项目/类型的自动导入，不得拉取全部任务后在本地过滤他人数据。
- 每个来源项目/工作项类型维护用户可配置的源状态排除集合。先从结果中的稳定状态标识过滤，再创建 Task 或派发 Agent；若 CTeam 搜索 API 能安全下推排除条件可作为优化，但结果正确性以集成侧排除为准。
- 经办人候选查询和状态排除是不同规则：当前用户 ID 通过真实“经办人”字段筛选；`userId` 认证 query 参数不能代替经办人条件。
- 插件负责 CTeam 认证、分页、当前用户与来源项目过滤、字段转换，不负责建立另一套任务列表。
- 不注册创建、更新、删除、时间写回等 CTeam 写能力；来源状态仅展示，不声明会改变 Task 完成状态的映射。
- 现有标题拉取行为不等同于本地修改保护，现有导入默认项目也不天然支持任意多项目路由。M0 须验证标题基线、跨映射去重、静默导入和项目路由，缺口只做最小通用宿主扩展。
- 内网 CTeam 的网络许可、固定可信来源和重定向行为须验证；不能把现有 HTTP 辅助工具当作完整 SSRF 边界。
- 确需核心专用实现时，先记录插件契约不能满足的具体证据及维护成本，再决定，不能仅因实现方便绕过插件路线。

### 8.2 Task 与 Renderer

- Task、Project 和其他可同步状态只有现有 NgRx / op-log 写入路径，Main 或新数据库不直接成为第二个任务写入者。
- Provider 数据先经过字段所有权和去重判断，再通过本地持久 Action 创建/更新 Task；相关原子变更遵循[贡献者同步模型](../sync-and-op-log/contributor-sync-model.md)。
- 派发分析只由当前执行设备上的本地导入/显式操作和经核对的持久队列触发；远端操作、启动 hydration 和重放不得重触发模型调用或补发任务写入。Effect 采用 `LOCAL_ACTIONS`，定时/selector 写入路径遵守同步窗口约束。
- Renderer 负责现有基本来源信息、Markdown 结果展示和轻量运行状态/筛选投影；经类型化、参数校验的 IPC 请求后台分析，不获得任意命令执行入口，也不将自由文本报告拆成必填业务字段。
- CTeam 凭证按第 5.7.1 节沿用受信任 Provider 的请求流程，不为“不接触 Renderer”另造一套认证代理。
- Task 行是高频渲染路径；AI 徽标使用预计算的轻量状态，不增加逐行轮询、模板函数/getter 或未清理订阅。

### 8.3 后台协调器与职责分工

| 所在层                                    | 职责                                                                             | 禁止越界                                                                           |
| ----------------------------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Issue Provider 插件与现有 Renderer 轮询层 | CTeam 候选发现、分页、来源映射、状态排除和已关联任务刷新                         | 不另起竞争的 Main Poller，不负责为 Pi 拼装完整工单                                 |
| Renderer 的现有任务状态层                 | 创建/更新 Task、标题保护、用户移动和来源关联                                     | 不绕过持久 Action 或直接写同步数据库                                               |
| Electron Main 或受控后台子进程            | 有限队列、Pi 子进程/Session 生命周期、配置的启动 `cwd`、提示词发送和本机报告存储 | 不操作代码仓库、维护 Git 状态或加 Project 级运行锁，不向 Renderer 暴露任意进程执行 |
| Pi 与本机 CWLink                          | 按链接读取工单，遵循用户的 `AGENTS.md` 使用仓库和 worktree 并分析代码            | 不向 CTeam 写回，不将认证秘密写入报告                                              |
| 现有详情、设置与通知层                    | 展示来源、报告和 Attention，编辑启动目录及提示词                                 | 不把 Pi 执行状态变成个人任务状态，不增加代码工作区管理台                           |

Renderer 提供当前 Task 的原始链接及 Project 配置，Main 在配置目录启动 Pi 并发送替换参数后的提示词。Pi 自行使用 CWLink 和本地代码；Main 只保存返回报告，再由 Renderer 核对 Task/运行关联后展示。不采集 HEAD/status/Diff，也不维护 worktree 创建、复用或清理记录。

IPC 只提供启动分析、停止和查询运行状态等有限能力；工单链接通过 RPC 消息传入 Pi，不在应用中拼接为任意 Shell 命令。

### 8.4 持久化、同步与保留边界

优先使用现有持久化机制。下列是逻辑记录，不预设 SQLite、新数据库或一张记录一种表：

| 数据                                                   | 唯一归属与跨设备规则                                                                                       |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Task 和必要来源关联、标题基线、删除/忽略抑制           | 复用应用状态/必要的最小扩展，沿既有同步与备份；不能同步运行队列                                            |
| CTeam 项目映射、工作项类型的经办人字段及源状态排除集合 | 以现有 Provider 配置为唯一事实来源；Project Settings 提供项目维度的编辑视图，不重复存储                    |
| Project 分析提示词                                     | 公司允许时沿现有应用同步，新增持久字段可选并提供默认；不包含 `AGENTS.md` 或代码工作区状态                  |
| Pi 启动目录、执行设备开关和项目分析授权                | 设备本地，不参与 SP 同步、导出和备份                                                                       |
| Pi Session、分析队列、运行记录、报告和事件摘要         | 设备本地，不默认跨设备同步或进入 SP 普通备份；其他设备不能伪装成已有运行                                   |
| CTeam 候选扫描检查点、待映射标识、诊断和来源缓存       | 按本机账号/实例/查询范围隔离。仅在 M0 证明增量游标语义后保存游标；否则记录完整分页扫描结果，不伪造增量游标 |
| CTeam 当前用户 ID 与凭证                               | 本机配置/秘密存储；不作为共享来源映射同步。Token 不参与 SP 同步、导出和备份                                |

**提交与恢复：**

- 只有 M0 已验证稳定增量游标后才推进游标；游标推进前，该范围内任务写入、必要关联和待映射记录须可靠持久化。仅收到 API 响应或 `dispatch` 返回不代表落盘完成；应用写入按需等待 `OperationWriteFlushService.flushPendingWrites()`。
- 任一候选分页或任务写入失败时，不得把该轮扫描标记为完成；按来源键幂等重试。若没有可靠增量接口，下一轮重新全量分页已授权项目中的“经办人为当前用户”候选；只有完整扫描后才记录完成时间。只有服务端确实提供可验证的增量过滤时，才额外处理时间戳精度、排序稳定性和分页边界。
- 删除/忽略记录只保存必要来源标识，不复制已删除任务；不能按普通缓存时间过期而使任务再次导入。M0 必须明确其容量上限和用户清理语义，达到上限时暂停新增自动导入，不静默丢弃抑制记录。
- 应用备份恢复只保证恢复纳入备份的 Task 和配置；本机报告、路径和凭证需要独立恢复或重新配置，不能把缺失的本机队列当作待执行任务自动回填。

**有限保留：**

以下为首期默认初值，M0 可根据代表性数据验证后调整并记录依据；普通缓存清理不能删除仍有效的来源关联或抑制记录。

- 每个 Task 默认保留最近 10 个报告版本，对应历史运行记录随报告清理；队列只保留活动、待执行和待核对项。执行事件仅保留摘要，默认最多 30 天且全局最多 10,000 条，不保存逐 token 事件或原始工具输出。
- 用户的 Project 工作目录、`AGENTS.md`、代码仓库及 worktree 不属于应用管理的数据；应用不设其磁盘配额、不跟踪状态，也不因 Task/Project 删除、完成或应用缓存清理而删除它们。
- Provider 按需来源缓存默认最多 7 天且总量不超过 100 MiB；先移除最旧的可重取缓存。Pi 经 CWLink 读取的内容由其本机配置处理，应用不另建一份全文缓存或代码快照。
- 新 Session 使用 Pi 的默认位置（通常为 `~/.pi/agent/sessions/` 下按启动工作目录分组）；Pi 的 `sessionDir` 设置或 `PI_CODING_AGENT_SESSION_DIR` 可覆盖。旧 Session 保留在 SP 本机 `pi-agent/sessions/` 并在继续分析时沿用；应用不自动迁移或删除历史文件。
- Pi Session 与其他 Pi 客户端共享存储；当前不扫描或限制整个 Pi 目录，也不自动清理会话。SP 同步、导出和普通备份不包含这些 Session，若需备份应单独备份实际 Pi 存储位置。手动打开或清理前须停止其他写入者。
- 删除 Task / Project 或断开集成时，提供相应本机分析资料的清理能力；清理会话和报告不得反向删除原生 Task。显式导出报告时说明其中可能包含公司内容。

不得建立完整的 `work_item`、`work_item_task` 或第二套 Project 表。首版来源界面只保存/展示必要基本信息；工单全文、评论和附件不为 UI 另建缓存，由 Pi 按需通过本机 CWLink 读取。

### 8.5 进程与平台边界

- 首期以 macOS / Windows Electron 为执行平台；Web / 移动端继续正常管理同步来的 Task，但不假定拥有本机路径、Pi、凭证或报告。
- 首期支持单执行设备模式：用户仅在选定的一台桌面设备启用 CTeam 自动轮询和 Pi 调度。执行开关本地保存，其他设备默认关闭；这不是分布式锁，不能宣称能自动阻止用户在两台设备同时启用。换机先关闭旧设备并核对未完成运行，不提供自动故障转移或跨设备运行接管。
- Pi 原生 RPC 是 `pi --mode rpc` 子进程的 stdin/stdout JSONL，不是默认监听端口的服务。JSONL 是通信封装，不要求模型的分析正文输出 JSON；正文始终按 Markdown 保存和展示。首期不增加网络监听；若未来确需网络桥接，需单独评审 loopback、认证和访问控制。
- Pi 作为用户安装并经确认的外部 Runtime 使用；启动前检测可执行入口、版本、所需 Node 运行环境、会话恢复和 RPC 能力。首期不为接入 SDK 向根依赖新增 Pi 包，也不自动下载安装资源。
- 托盘常驻依赖保留的应用进程和 Renderer，而非 Task Detail 页面。窗口隐藏但应用仍在运行时继续已授权轮询/调度；Renderer 崩溃或状态未就绪时暂停新的派发。
- 真正退出应用时持久化队列、取消未完成运行并关闭 Pi 子进程，不承诺退出后继续工作；需验证 Windows 进程树退出和 macOS 生命周期，不遗留失控子进程。

## 9. CTeam API 前置验证（M0）

本机已有 CWLink 实现可作为 API 调用和字段归一化的参考基线（`D:/workspace/canway/cwlink`，检查时 HEAD 为 `ada44be`；其 `docs/development/cteam-real-data-survey.md` 记录了四类工作项的真实只读样本）。这是实现参考和已观察到的契约，不等于当前公司部署的官方版本保证；M0 应复用已知信息，优先验证部署差异和本需求尚未覆盖的能力，不必从零猜接口。

### 9.1 已有参考基线

- CWLink 当前 CTeam Client 的默认 DevOps 入口为 `https://devops.cwoa.net`。认证使用用户 ID 和 DevOps Access Token；请求携带 `X-DEVOPS-UID`、`X-DEVOPS-ACCESS-TOKEN`，可选 `X-DEVOPS-TENANT-ID`，并在 URL query 中带 `userId`。服务地址在 CWLink 中为内置值，不从这个参考推导出应允许任意 URL 配置。
- 精确详情读取：`GET /api/open/CTeam/api/service_open/issue/2.1.0/{projectKey}/{issueId}`。响应的 `data.property` 包含动态字段映射；公共字段样例含内部 `id`、项目、编号、`modelTypeId`、标题、状态、优先级、描述和 `updateTime`。动态字段保留 id/name/label/type/value/displayValue，不应依赖固定全字段白名单。
- 项目内分页搜索：只读用途的 `POST /api/open/CTeam/api/service_open/issue/2.1.0/flat?num={zeroBasedPage}&size={pageSize}`，body 为 `{ name, value: [...] }` 过滤器数组。已有调用以 `projectId`（URL 中的 CTeam 项目键）过滤，也支持按 kind 加 `typeClassify`、`modelTypeId`，响应包含 content 与总页数/总数。该 POST 是查询，不是工单写入。
- 动态搜索字段：`GET /api/open/CTeam/api/user/issue_field/{projectKey}/query_filters?classify={BUG|DEMAND|TASK}`。CWLink 仅在项目返回字段并验证匹配后才把动态字段用于筛选；可供 M0 探测“经办人”候选字段，但尚未证明其筛选值形状可准确表示当前用户。
- CWLink 已有详情、评论和附件读取实现，可作为能力参考：评论 `GET /api/open/CTeam/api/user/issue_comment/{projectKey}/{issueId}`；附件清单 `GET /api/open/CTeam/api/service_open/issue_file/2.1.0/{projectKey}/{issueId}`；附件二进制走对应的 `file/2.1.0/{projectKey}/download/{fileId}`。首版来源界面不实现评论或附件阅读/下载；Pi 如需这些信息，直接按用户指引使用本机 CWLink，不在应用内重复实现分析取数管道。
- 本地参考样本涵盖 Bug、ITR、需求和 Task。CTeam kind 需结合详情 `modelTypeId`，例如 ITR 和普通缺陷都可能属于 `typeClassify=BUG`；样本中的具体 modelTypeId 不是不经验证的全局配置。

### 9.2 M0 仍须在当前部署实证

- 当前 CTeam 部署是否与 CWLink 的 DevOps host、认证头、tenant 和 OpenAPI 路由版本一致；当前用户身份、Access Token 生成/失效、权限范围及服务审计要求。若 host 不同，应先确认可信固定部署和网络策略，不直接开放任意服务地址输入。
- 不设计专用“我的工单”接口；候选发现通过 `query_filters` 返回的动态“经办人”字段和当前用户 ID 搜索。M0 按每个来源项目及 `modelTypeId` 验证字段 ID、筛选值编码（用户 ID/对象值）、多经办人、转派、候补经办人与搜索结果，证明不会匹配其他人员或遗漏当前用户工单。若 exact match 不能证明，停止该项目/类型的自动导入。
- 对每个项目/`modelTypeId` 读取实时状态选项，识别代表“已完成”“已关闭”“测试完成”等需排除的终态；以用户确认的稳定状态 ID 配置排除，显示名可本地化。验证搜索 API 是否支持服务端排除；若不支持，必须在完整读取经办人候选页后、Task 创建前本地过滤，不得把未排除的项目写入 SP 或触发 Pi。状态映射变化/缺失时暂停该来源范围并提示复核。
- **目前仅有分页基线，没有已证实的增量游标契约。** 当前列表接口支持 `num/size` 分页及 `totalElements/totalPages` 一类分页摘要；CWLink 代码没有实现稳定 cursor 或 `updatedAt` 增量调度。虽有详情 `updateTime`，仍须验证搜索端是否支持可靠时间过滤、排序稳定性、同时间戳边界及写入期间分页是否漏项。没有可靠增量查询时按授权项目全量分页扫描并本地去重，不能承诺严格增量同步。
- 结合当前真实工作项验证内部 `issueId`、project key 与显示编号的关系，字段 `updateTime` 变化规则，以及状态/优先级的项目级字典；分别确认关闭、取消分配、删除和无权限的可观测性。
- Pi 如需通过 CWLink 读取评论或附件，复核其已有能力的权限和下载边界，不将应用内评论/附件展示或解析作为首版前置工程。验证 CTeam POST 搜索是只读查询；本需求不调用创建、更新、评论写入、关系变更、流转、上传或删除接口。
- 公司对工单进入 SP 同步/导出/备份以及工单或代码发送到模型服务的数据政策。API 可调用不等于组织批准数据用途。

M0 对每项结论注明“CWLink 已实现参考”“当前公司部署已验证”或“仍未知”，并用脱敏请求/响应和测试记录证明。不得复制真实 Token 或工单敏感内容。经办人筛选必须在服务端候选查询中生效；状态排除可在服务端实现，也可在完成所有经办人候选分页后、创建 Task 前本地实施。没有可靠增量接口时，可定期全量分页经办人候选并本地去重；分页不完整不能推进扫描完成标记，更不能把未出现的工单视作关闭/删除。不得把临时抓包接口当作长期契约，除非已确认公司允许且稳定。

## 10. 隐私、安全与合规

- 自动发现仅限当前用户被分配且有权访问的工单；对既有工单的状态复查也必须在公司允许范围内，不扩大到其他人的全量工单。
- 使用最小权限只读凭证，由项目本机秘密存储管理，不强制系统钥匙串；真实安全等级和限制见第 5.7.1 节。
- 原生 Task 的标题等工单资料会随 SP 数据集同步、导出和备份。导入前必须确认现有目的地符合公司政策；不能仅保护 Token，或假定“来源只读”就不会向其他系统复制数据。
- 未获允许时不导入该数据集；需要隔离时可使用独立应用配置/数据集，首期不另建复杂的逐 Task 同步排除体系。
- 本地运行 Pi 不代表本地推理。发送工单、Project 知识或代码前，明确允许的模型服务、资料范围和用途；没有授权不发送，启用工单导入不等于启用自动分析。
- 日志只记录必要 ID、状态、错误分类和时长，不记录 Token、认证 Header、工单标题/全文、附件内容、完整工具参数或代码内容。报告和 Pi Session 本身可能包含敏感资料，受独立的本机保留与显式导出规则约束。
- 来源 Markdown、模型报告和链接按不可信内容处理；附件按需下载，校验来源、大小和类型，不能携带认证 Header 跟随到不可信目标。
- Pi 的仓库、命令和 worktree 使用沿用用户本机配置及 `AGENTS.md` 约定，应用不另建逐项权限编排。该约定不是安全沙箱，不能绕过 CTeam 只读边界；实际验证与建议必须如实区分。
- 不向 CTeam 写回，不执行未经授权的外部操作；撤销授权后停止受影响运行，但不得宣称能撤回已经发送到模型、同步端或备份中的资料。

## 11. 里程碑与验收标准

按“导入与来源展示 → 本机 CWLink + Pi 手动分析 → 授权自动分析 → 筛选增强”交付。先证明链接到代码分析的最小闭环，不把 Git 状态维护、worktree 编排或自定义权限工具作为首期前置工程。

### M0：代码结构、API 与最小分析闭环验证

- 记录当前仓库 commit、Pi 和 CWLink 版本；检查 Task / Project 的模型、持久化、同步和插件接入入口。
- 以本机 CWLink `ada44be` 为 CTeam 接口参考，验证当前部署差异；用真实 CTeam 身份验证动态“经办人 = 当前用户”搜索和用户配置的状态排除集合。
- 优先验证 Provider 插件对多项目导入、来源身份、标题保护、静默导入、删除/归档及本机秘密存储的复用点和最小缺口，不绕过插件路线。
- 确认现有 Project Settings、来源详情和 Task AI 面板入口；Pi 侧只增加本机启动目录、可编辑提示词和必要运行配置。
- 使用真实工单链接验证：在配置目录启动 Pi，读取用户的 `AGENTS.md`，调用本机 CWLink 取得工单并分析代码，将模型自由输出的 Markdown 返回 Task Detail；验证无需固定 JSON、字段或章节。记录本机 CWLink 入口和已有认证配置要求，不复制凭证。
- 在 macOS / Windows 验证 Pi 子进程 RPC、Task 独立 Session、恢复、停止及退出；验证同 Project 的不同 Task 可以并行，不设置 Project 锁。
- 由用户的 `AGENTS.md` 约定代码位置与独立 worktree 使用；应用不创建或跟踪 worktree、不采集 Git 状态、不自动更新或清理代码，也不改写指引文件。
- 明确 CWLink 不可用、认证失败、无效链接或缺少代码时的报告方式；失败时不伪造成功，不增设分析取数代理作为自动 fallback。
- 按第 9 节实测 Provider 经办人字段、排除状态 ID、分页一致性和增量条件；无可靠增量接口时采用授权范围内全量分页与幂等去重。
- 验证凭证不进入 SP 同步/导出/备份、Pi 提示词或日志；CWLink 与 Provider 各用已有本机认证，不强制系统钥匙串或新凭证代理。
- 输出最小文件级改造清单、数据归属和故障用例；不要将本机 Agent 工作方式扩张为应用内 Git 管理或通用 Agent 平台。

### M1：CTeam 原生 Task 与来源详情

验收：

- 配置位于现有集成和 Project 设置中，通过本机凭证管理完成认证；只通过已验证的“经办人 = 当前用户”搜索获取获准范围内的候选工单。
- 多个 CTeam 项目可汇入同一个 SP Project；同一来源项目映射冲突被明确拒绝。
- 工单沿现有导入路径创建为 Task；首版详情来源区域仅展示工单编号、工单标题、CTeam 来源状态和原始链接，不增加描述、评论、附件列表或下载入口。
- 经办人字段精确筛选当前用户；按配置排除已完成、已关闭、测试完成等源状态的候选，不创建对应 Task、不派发 Pi。重复分页、重启、归档、用户删除/忽略和显式重新导入均有确定行为，不重复创建或擅自复活任务。
- 已导入 Task 后续进入排除状态时保留本地 Task，不自动完成/归档/删除；刷新其已知来源状态并停止自动分析。
- 标题三方比较保护本地改名；来源刷新不覆盖 Notes、子任务、标签、计划、时间记录、用户移动和完成状态。
- 未映射项目可在补齐后重新查询并补导；部分分页或任务写入失败不将该轮扫描标记完成，缺席/权限错误不被当作删除。
- 用真实导入/刷新路径的测试覆盖上述行为，并验证原有普通任务、旧数据加载及应用同步/备份无回归。

### M2：手动 Pi 分析与本机 CWLink

验收：

- 每个 Project 可配置本机 Pi 启动工作目录和分析提示词；同 Project 的所有 Task 使用同一配置，Pi Session 按 Task 独立。
- 用户从原生 Task Detail 手动启动分析；应用发送工单原始链接和提示词，不先抓取并拼装完整工单。
- Pi 读取用户维护的 `AGENTS.md`，通过本机 CWLink 取得工单，按约定访问本地代码并返回报告；不要求在 SP 中配置 GitLab Token。
- 同 Project 的不同 Task 可以并行；用户可约束 Pi 使用独立 worktree。应用不加 Project 级串行锁，也不管理 worktree、代码更新、HEAD/status/Diff 或指引文件。
- 启动目录、Pi/CWLink 不可用、读取工单失败或代码缺失时如实报告阻塞；应用不声称已完成代码分析。
- Task Detail 直接保存并展示模型最终输出的 Markdown 及独立运行信息，不要求固定 JSON、章节或字段；不自动改写 Notes、个人完成状态或 CTeam。
- 支持停止、进程中断后的核对和恢复；不能把 RPC 接受响应当作完成。
- 首个闭环不要求新增工单内容代理、附件解析器、Diff UI、独立 Git 权限系统或完整会话管理界面。

### M3：授权自动分析与报告版本

验收：

- 用户在 Project 明确启用自动分析后，新发现且符合范围的工单可排队；首次历史导入不产生未确认的批量模型调用。分析仍使用配置的提示词、本机 CWLink 和用户维护的指引。
- 同一 Task 的重复自动请求合并；同 Project 的不同 Task 可以并行，仅受全局可配置并发上限约束。
- 新请求、Project 移动、停止和授权撤销期间的迟到结果不覆盖当前报告、不复活任务、不重复通知；旧报告可按保留规则查看。
- 报告有效性只基于应用已知的来源与请求变化；不扫描代码或 `AGENTS.md`，不维护代码版本与变更指纹。
- 测试接受请求后崩溃、完成后未落库、重启和旧会话核对路径；无法确认时标记中断，不盲目重发。
- 应用同步、远端重放、hydration 和其他设备打开 Task 不触发重复分析。
- Task Detail 支持继续、重新分析、停止和有限历史；交互打开同一 Pi Session 时不与后台运行同时写会话文件。

### M4：原生筛选、通知与可观测性

验收：

- 现有筛选可按来源、运行状态、报告有效性和 Attention 定位原生 Task；其他平台/设备正确显示能力不可用。
- 原有 Boards 继续混合显示普通和 CTeam Task，不新增强制列，标识不影响拖拽和状态操作。
- 系统通知默认关闭；启用后仅按用户选择的原因提醒，确认和轮询不会产生重复通知。
- 现有设置/诊断可查看同步结果、有限队列、失败分类、显式重试和清理入口，不展示凭证或原始用户内容。
- 全局 Agent 指示器保持可选、轻量；大任务列表验证无逐行轮询、额外订阅或明显渲染退化。
- 凭证、设备配置、报告/事件/Session 的同步与导出边界、容量限制和清理行为有对应验证。

### 后续范围

第一版不建设测试执行面板、Git 提交/推送/MR 管理界面或通用 Agent 权限编排。Pi 可按用户已有的本机配置和指引使用工具，这不要求应用增加对应工作流；CTeam 仍保持只读。

## 12. 待确认事项

以下是需要 M0 获取证据的未知项，不再把已明确的产品决定留作开放选择：

1. 当前公司 CTeam 部署是否与 CWLink 参考的 host、认证、tenant 和 OpenAPI 路由一致；动态“经办人”字段的精确匹配与“分配给当前用户”的真实语义。
2. 每个来源项目/`modelTypeId` 的状态选项 ID，以及默认排除“已完成”“已关闭”“测试完成”是否符合实际工作流；状态变更后的既有 Task 处理规则。
3. 当前工作项查询是否提供稳定增量过滤/排序；否则确认全量分页频率、上限和可接受的同步延迟。
4. 当前项目内部 `issueId` 的唯一范围/稳定性、project key 映射，以及各类 work item 的状态/优先级字典。
5. 当前插件契约对多项目路由、标题保护、静默导入、删除抑制和凭证界面的具体缺口。
6. 公司允许的 SP 同步/备份目的地、模型服务，以及可进入模型的工单、Project 文本和代码范围。
7. 各设备的 Pi/CWLink 实际启动入口及工作目录是否可用，真实工单链接能否由本机 CWLink 读取；代码和 worktree 的约定由用户维护，不作为应用配置协议。
8. Project 工作目录和可编辑提示词的最小存储位置、设备本地边界及旧客户端兼容性。
9. Pi 最低兼容版本、Session 恢复、全局并发预算和 macOS / Windows 进程生命周期验证结果。
10. 本机 CWLink 对真实工单链接、评论和附件的已有读取能力及失败表现；第一版不在应用内补建分析内容抓取链路。
11. 删除/忽略抑制记录的有限容量与清理语义，及设备迁移时需由用户确认的本机状态。

首期已确定：CTeam 插件优先；允许项目管理本机凭证；Pi 使用本机子进程 RPC；每 Project 配置启动目录和提示词；Pi 经本机 CWLink 读取工单，用户自行维护 `AGENTS.md` 和 worktree 约定；不同 Task 可并行，应用不加 Project 锁或维护代码状态；仅指定桌面设备自动执行，真正退出后不继续运行；先手动闭环再开放授权自动分析。

## 13. 最终产品验收原则

完成后，用户应该仍然只使用 Super Productivity 原来的工作方式：

- 打开原有 Task List，就能看到导入的 CTeam 工单和普通任务。
- 打开原有 Project，就能看到映射到该项目的工单、项目级 CTeam 关联和本机 Pi 配置。
- 使用原有 Board、Planner 和 Time Tracking 管理 CTeam Task。
- 打开原有 Task Detail，就能看到外部工单信息、AI 分析和 Pi 执行摘要。
- 使用现有筛选找到 CTeam Task、分析中任务或需要人工介入的任务。
- 一个原有 Project 可以组织普通 Task 和多个 CTeam 项目的工单；Pi 按该 Project 的启动目录、提示词和用户维护的 `AGENTS.md` 使用一个或多个代码仓库。
- 同一 Project 的 Task 共用配置的 Pi 启动目录但各有独立 Session，可以并行；独立 worktree 等代码工作方式由 Pi 按用户指引执行，应用不代管。未启用 AI 时仍可正常管理任务。
- 不需要维护第二套 Inbox、第二套看板、第二套 Task 状态或第二套项目体系。

**最终目标：让 Super Productivity 原有 Task 获得外部工单同步、AI 理解和 Agent 执行能力，而不是让用户学习和维护另一套工作管理产品。**

## 14. 当前本机试用问题记录（2026-11-03）

- **现象**：首次配置 CTeam Issue Provider 时，“加载选项失败”，且“测试连接”未通过。
- **根因**：状态下拉选项的加载路径误用了要求经办人字段已选的完整配置校验；但经办人字段本身也要先加载选项才能选择，形成先后依赖。
- **源码处理**：工作区已修改为允许在经办人字段选择前加载动态选项；实际搜索和连接测试仍要求用户明确选择经办人字段。包测试覆盖该顺序。
- **搜索错误实测**：用户导出的日志记录 `[PluginIssueAdapter] searchIssues failed for plugin:cteam-issue-provider`，插件失败原因为“CTeam did not confirm exact current-user/project/type filtering. Import stopped.”。CWLink 只读核对确认，CTeam 的 USER 类型“经办人”字段可将多个用户 ID 编码为逗号分隔字符串；原插件只把整个字符串与当前用户 ID 全等比较，没有识别集合成员，因而会拒绝包含当前用户的记录。Provider 搜索会先扫描和校验该范围的候选分页，之后才按输入标题/编号本地过滤，因此其他候选行的多值经办人也会导致单条搜索失败。真正空结果应返回空列表，而非该校验错误。
- **安全边界**：该校验是失败关闭，不能为了让导入继续而移除。修复需按逗号拆分后精确比较各用户 ID，不以子串、显示名或宽松匹配代替身份检查。

## 15. 新单自动流程补充（2026-11-04）

- **链接修正**：以用户提供的可跳转地址为依据，工单链接使用对应的 twBug / twDemand / twTask 路由，并同时包含 vmode=table 与内部工单 id；不把展示编号当内部身份，也不携带凭据。
- **自动首次分析**：复用 Project 现有的本机 Pi 启用配置；本机成功新建 CTeam Task 后发出一次非持久化导入事件，协调器读取目标 Project 配置，自动启动独立 Task Session。没有新增 Task/Project 同步字段、同步操作或公共插件 API。
- **通知**：Project 本机 Pi 设置中增加可独立启用的新单通知开关，旧配置缺少该字段时按关闭处理。通知合并同批、同 Project 导入，不显示工单内容；通知异常不影响导入或分析。
- **重放边界**：启动、同步、恢复、已有任务刷新和重复来源去重均不发布新建导入事件。不会自动重放失败、中断或已有运行，不扫描旧 Task 补跑。
- **保持简化**：不同 Task 可并行，不新增 Project 锁、Git/worktree 管理、报告 schema、后台队列、通知中心或自动整轮重试。手动重试、Session 继续及终端恢复保留。
- **安装与验证边界**：以上是本次源码变更范围，不表示已替换正在使用的本机安装或完成真实 CTeam / CWLink / 模型联调；验证结果须按实际执行报告。
